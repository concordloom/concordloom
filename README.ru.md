# Concord Loom

## Системы, которые умеют менять себя — но не могут сами себе это разрешить.

[![CI](https://github.com/PullDakar/concordloom/actions/workflows/ci.yml/badge.svg)](https://github.com/PullDakar/concordloom/actions/workflows/ci.yml)
[![Pages](https://github.com/PullDakar/concordloom/actions/workflows/pages.yml/badge.svg)](https://github.com/PullDakar/concordloom/actions/workflows/pages.yml)
[![License: Apache-2.0](https://img.shields.io/badge/license-Apache--2.0-c8ff00.svg)](LICENSE)

**Concord Loom — независимый от предметной области фреймворк для исследования,
согласования, связывания, исполнения, проверки, визуализации и эволюции
конечных систем циклов.**

```text
НАБЛЮДАТЬ → СОГЛАСОВАТЬ → СВЯЗАТЬ → ИСПОЛНИТЬ → ПРОВЕРИТЬ → ОПУБЛИКОВАТЬ? → РАЗВИВАТЬ
   факты        намерение     правила       эффект       доказательство   полномочие       предложение
```

Вопрос не в том, есть ли в вашей работе циклы. Они есть.

Вопрос в том, можно ли установить:

- что наблюдалось, а что было лишь предположено;
- кто принял намерение;
- какая точная политика и какой candidate исполнялись;
- какие доказательства выполнили заявленный контракт;
- где заканчиваются повторы;
- и кто вправе разрешить следующую версию системы.

Concord Loom делает эти границы явными и адресуемыми по содержимому.

> **Это не SDLC-фреймворк.** Поставка программного обеспечения — один пример
> binding наряду с исследованиями, реакцией на инциденты, творческим
> производством, управлением и любым другим ограниченным процессом, который
> явно примет оператор.

## Одна грамматика, много систем

| Область | Один из возможных bindings |
|---|---|
| Исследование | гипотеза → эксперимент → доказательство → пересмотр |
| Реакция на инциденты | сигнал → локализация → восстановление → обучение |
| Творческое производство | бриф → исследование → критика → результат |
| Управление | наблюдение → предложение → решение → эффект |
| Поставка ПО | требования → реализация → тестирование → релиз |

Слова меняются. Инварианты остаются: конечный containment, явные полномочия,
ограниченная обратная связь, доказательства, привязанные к candidate, и
терминальные исходы.

## Модель двух графов

Concord Loom не прячет две разные структуры внутри одной «workflow»-схемы:

1. **Containment-граф** определяет, какой цикл уточняет составной шаг. Он
   конечен и ацикличен.
2. **Локальный граф управления** цикла может содержать обратную связь, но у
   каждого повтора есть бюджет и путь к успеху, ошибке или эскалации.

Дочерний цикл сообщает, что он установил. Родитель решает, что означает этот
результат. Зелёная квитанция дочернего цикла не превращается в полномочие
родителя по умолчанию.

## Попробовать

Достаточно Python 3.11+ и Git. Переносимое ядро использует только стандартную
библиотеку.

```bash
python3 -m pip install \
  "concordloom @ git+https://github.com/PullDakar/concordloom@v0.1.0"

mkdir -p .concord/discovery
concordloom inspect . \
  --output .concord/discovery/observed-project-graph.json
concordloom questions \
  --graph .concord/discovery/observed-project-graph.json \
  --output .concord/discovery/questions.json
```

Эти команды создают наблюдения и вопросы — **не принятое намерение**.
Значимые решения должен принять оператор.

Продолжите по [руководству быстрого старта](docs/ru/QUICKSTART.md) или откройте
[интерактивный сайт Concord Loom](https://pulldakar.github.io/concordloom/).

## Цепочка артефактов

```text
данные репозитория
  ↓
наблюдаемый граф ──→ ранжированные вопросы
  ↓                         ↓
решения оператора ──→ принятый граф
  ↓
предложение дизайна циклов ──→ явное принятие дизайна
  ↓
registry + binding proposal ──→ отдельная активация binding
  ↓
candidate + run + evidence ──→ генерируемый Atlas
  ↓
повторяющиеся сигналы ──→ successor proposal ──→ отдельное решение оператора
```

Каждая стрелка создаёт новый артефакт. Поздние стадии ссылаются на точные
digest и не переписывают исходные наблюдения.

## Concord Loom управляет Concord Loom

Проект использует собственный универсальный self-binding:

`Observe → Negotiate → Bind → Execute → Verify → Publish? → Evolve`

Первая самоэволюция проекта обнаружила реальный governance deadlock в исходном
generic-SDLC binding: он мог предложить изменение, но его scope не позволял
материализовать преемника или опубликовать сайт. Исправление тоже прошло как
проверяемая цепочка:

- два независимых сигнала отказа;
- evolution proposal без права активации;
- явное принятие универсального дизайна оператором;
- отдельное решение об активации точных байтов;
- successor в append-only каталоге;
- раздельные области исполнения, независимой проверки и публикации.

Эволюция может предложить преемника. **Она не может сама его активировать.**

## Команды

| Команда | Результат |
|---|---|
| `inspect` | наблюдаемый и предполагаемый граф репозитория |
| `questions` | ранжированные вопросы о намерении |
| `decide` | одно явное решение оператора |
| `accept` | принятое намерение или дизайн циклов |
| `propose` | проверяемое предложение дизайна |
| `compile` | registry циклов и binding proposal |
| `activate` | binding, принятый отдельным решением |
| `catalog` | append-only цепочка активных bindings |
| `candidate` | адресуемый по содержимому manifest candidate |
| `run` | управляемый жизненный цикл запуска |
| `atlas` | детерминированная offline-проекция |
| `evolve` | предложение преемника — никогда не активация |
| `validate` | проверка схем и связей между артефактами |

```bash
codex plugin marketplace add PullDakar/concordloom --ref v0.1.0
codex plugin add concordloom@concordloom
```

Попросите Codex использовать `$design-project-loops`. Навык начинает с
ограниченного read-only исследования и не превращает историю репозитория в
намерение без решения оператора.

## Граница доверия

Concord Loom проверяет декларативные артефакты, инварианты графов, scopes,
контракты доказательств и разделение полномочий. Он не является OS sandbox,
провайдером учётных данных, долговечным workflow engine или сервисом
криптографической идентификации. Системы с высокими последствиями должны
добавить платформенное принуждение и подписанные attestations согласно своей
модели угроз.

Перед управлением значимыми эффектами прочитайте
[модель доверия](docs/ru/TRUST_MODEL.md).
