# Предложение по фронтенд-циклу

Язык: [English](../FRONTEND_CYCLE_PROPOSAL.md) | **Русский**

Статус: **только предложение — не активировано**

Основа: действующая конфигурация Concord Loom v9

## Какое решение нужно принять

Усилить существующий фронтенд-цикл, не добавляя и не удаляя циклы.

Нынешней структуры достаточно. Проблема была в правилах приёмки: страница
могла исправно открываться, но заметно отличаться от принятой концепции. После
обновления такую работу нельзя будет назвать завершённой.

## Что должен получить пользователь

Каждое изменение интерфейса должно заканчиваться одной точной версией, которая:

- следует принятой визуальной концепции на всех публичных страницах;
- работает при размерах 360×800, 390×844, 844×390, 768×1024, 1024×768,
  1440×900 и 1920×1080;
- работает на русском и английском, а при первом открытии выбирает английский;
- остаётся понятной без JavaScript;
- честно показывает загрузку, отсутствие данных, устаревшие данные и ошибки;
- работает с клавиатуры, при масштабе 200% и с отключённой анимацией;
- сохраняет адрес, историю браузера, язык и положение в Атласе;
- не содержит наложений, обрезанных подписей, случайной горизонтальной
  прокрутки, двойной навигации, неработающих элементов и целей меньше
  44×44 пикселей;
- даёт текстовое или древовидное представление любого интерактивного графа;
- проходит независимое визуальное сравнение с принятой концепцией, а не только
  со своим предыдущим снимком.

## Существующий цикл с более строгими правилами

### 1. Определить визуальную концепцию

Превратить цели продукта и референсы в единый визуальный контракт. Он фиксирует
композицию, иерархию, изменения на разных экранах, состояния компонентов,
движение, запреты, поддерживаемые размеры и доказательства для приёмки.

`ui-ux-pro-max`, дизайн-система Concord Loom и подходящие дизайнерские
инструкции подключаются как зафиксированные ресурсы. Автоматическая рекомендация
помогает принять решение, но не становится вторым источником правил.

### 2. Принять визуальную концепцию

Оператор принимает или отклоняет точную версию контракта. Текст и снимки,
которые не относятся к этой версии, не заменяют решение.

### 3. Поддерживать мастерскую интерфейса

Мастерская использует те же токены и стили компонентов, что и сайт. Она
показывает обычное, наведённое, выбранное, нажатое, отключённое, загружаемое,
пустое, ошибочное и устаревшее состояния, длинный текст, русский и английский
варианты. Макет с отдельными стилями не считается доказательством.

Storybook необязателен. Пока компонентов немного, самостоятельная мастерская
проще и дешевле. Storybook стоит подключить, когда количество компонентов или
участников оправдает дополнительную зависимость.

### 4. Собрать версию интерфейса

Сайт собирается только по принятому контракту и из компонентов мастерской.
Адрес страницы должен сохранять выбранный раздел, цикл Атласа, язык и открытые
состояния, которые нужно восстановить. Технические данные доступны, но не
мешают основному сценарию.

### 5. Поддерживать браузерные проверки

Проверки охватывают точные размеры и языки, работу без JavaScript, загрузку и
ошибки, клавиатурный фокус, изоляцию модального окна, минимальный размер целей,
геометрию графа, столкновения подписей, историю браузера, масштаб, отключённую
анимацию и доступность.

Playwright MCP помогает автору исследовать интерфейс. Источником проверки
остаются воспроизводимые тесты Playwright и точные артефакты.

### 6. Проверить версию в браузере

Проверка без языковой модели запускает зафиксированный набор тестов для точной
версии. Она сохраняет снимки, геометрию, результаты проверки доступности,
состояния исполнения и список контрольных изображений с SHA-256. Проверка не
может сама обновлять свои эталоны и не выносит вкусовых суждений.

### 7. Независимо проверить качество

Новый критик с высоким уровнем рассуждения сравнивает точные концепцию,
контракт, версию и полную матрицу снимков. Он проверяет визуальное соответствие,
иерархию, понятность, русский текст и цельность продукта.

Возможны три вердикта: `PASS`, `REVISE` и `INDETERMINATE`. Успешные
механические проверки не отменяют `REVISE`.

## Граница доработок

После `REVISE` версия возвращается в разработку. Проверка и независимая критика
повторяются уже для новой версии. После трёх неудачных попыток работа
останавливается, а оператор решает, что менять: концепцию, реализацию или
правила приёмки.

Агент не может незаметно ослабить визуальный контракт, заменить контрольные
снимки ради сокрытия ошибки или принять собственную работу.

## Расход моделей и ресурсов

| Работа | Основной маршрут |
|---|---|
| Концепция, мастерская и реализация | Terra, средний уровень рассуждения |
| Развитие браузерных проверок | Terra, низкий уровень рассуждения |
| Воспроизводимые браузерные проверки и хеши | Без модели |
| Разбор обычных ошибок | Luna с низким уровнем рассуждения, если модель вообще нужна |
| Финальная независимая критика | Sol с высоким уровнем рассуждения |
| Проверка русского интерфейса и документации | `ru-text`; Sol подключается только для спорного и важного текста |

Дорогая модель работает там, где требуется суждение, а не на каждом изменении
CSS или теста.

## Какие доказательства обязательны

К одной точной версии должны относиться:

1. хеш принятого визуального контракта;
2. исходники и сгенерированные файлы сайта;
3. мастерская с компонентами продукта;
4. набор браузерных проверок;
5. снимки всех принятых страниц, языков, состояний и размеров;
6. список контрольных снимков с хешами;
7. результаты воспроизводимых проверок;
8. заключение независимого критика.

Публикация остаётся отдельным действием с отдельным разрешением. Успешная
проверка интерфейса не даёт права разворачивать сайт.

## Что предлагается изменить в следующей версии

Если предложение будет принято, следующая конфигурация должна:

- сохранить нынешнюю структуру `design-site-experience`;
- закрепить `ui-ux-pro-max`, `ru-text`, правила дизайн-системы и браузерный
  адаптер как версионированные ресурсы там, где они используются;
- заменить расплывчатые результаты точным набором доказательств выше;
- явно зафиксировать предел в три доработки и путь возврата;
- требовать отрицательные проверки геометрии, взаимодействия и языка;
- отклонять заключение критика, если он же создал проверяемую версию;
- везде одинаково указывать публичную команду проверки:
  `python3 -m concordloom run guard`.

Активация остаётся отдельным решением оператора. Этот документ не меняет
действующую конфигурацию.
