# Основные понятия

[English version](../CONCEPTS.md)

Concord Loom описывает работу как конечную систему циклов, вложенных друг в
друга. Он не требует конкретной предметной области, движка, среды исполнения,
поставщика моделей или структуры репозитория. Жизненный цикл разработки ПО
(SDLC) — один из примеров такой конфигурации, а не определение продукта.

## Система ограниченных циклов

Цикл получает объявленный вход и должен прийти к одному из конечных исходов.
Заранее заданы требования к проверке, полномочия, разрешённые действия и
бюджеты. Родительский цикл может поручить часть работы дочернему. Один и тот же
контракт действует на любом уровне, но число уровней всегда конечно.

Поставляемый пример generic SDLC показывает требования, реализацию,
тестирование, выпуск и эксплуатацию как вложенные циклы. По той же модели можно
связать исследовательский процесс, производство контента, аттестацию
оборудования, реагирование на инциденты или смешанный процесс с участием людей
и машин.

## Вложенность и обратная связь — разные графы

Concord Loom хранит два типа связей:

- `contains(parent, child)` задает конечное ациклическое уточнение и ограничивает
  глубину вложенного исполнения;
- локальный граф состояний цикла может содержать обратные переходы, но каждый
  циклический компонент обязан уменьшать конечный бюджет попыток, времени,
  стоимости или инструментов и сохранять путь к завершению либо эскалации.

Если назвать обе связи рекурсией, исчезает важное свойство безопасности. Атлас
показывает их по-разному.

## Контракт цикла

Контракт определяет:

- типизированные описания входов и выходов;
- единственную точку входа, состояния, декларативные переходы и терминальные
  результаты;
- вызовы дочерних циклов, отображение данных, срок и отмену;
- условия успешной проверки;
- необходимые возможности и правила независимости;
- бюджеты попыток, времени, стоимости и инструментов;
- эскалацию, если безопасное завершение невозможно.

Валидатор отклоняет циклическую вложенность, недостижимые состояния,
нетерминальные тупики, обратную связь без бюджета, исчерпание без выхода,
расширение дочерних полномочий и самопроверку автора там, где нужна
независимость.

## Квитанция дочернего цикла не решает за родителя

Дочерний цикл сообщает результат и указывает вход, проверяемую версию,
политику, исполнителя и данные проверки. Родитель оценивает этот отчёт по
собственным правилам.

Отдельный сценарий может пройти, а вся кампания — остаться открытой. Кампания
может пройти, а публикация — остаться неразрешённой. Отчёт дочернего цикла
подтверждает только свою часть работы: он не расширяет полномочия и не закрывает
родительский цикл автоматически.

Исполнитель v0.1 записывает попытки и данные проверки для запланированных
узлов. Он не создаёт отчёты дочерних циклов за внешние системы, не проигрывает
каждый локальный переход и не запускает долговечные дочерние процессы. Адаптер
возвращает родителю данные для конкретной проверяемой версии; решение о
завершении остаётся за правилами родительского цикла.

## Эпистемические состояния

| Состояние | Значение |
|---|---|
| Наблюдаемое | Получено непосредственно из объявленного источника |
| Предполагаемое | Гипотеза с происхождением и уверенностью |
| Принятое | Намерение, одобренное уполномоченным оператором |
| Запланированное | Предполагаемый маршрут, область, модель, инструмент или проверяющий |
| Фактическое | То, что записала попытка |
| Проверенное | Данные проверки выполнили связанные требования |
| Расхождение | План и факт не совпали |

Адаптер наблюдения может читать Git-репозиторий, хранилище артефактов, API
сервиса или другой ограниченный источник. Уверенность влияет только на порядок
вопросов и никогда не дает полномочий.

## Три рубежа принятия

1. **Принятие намерения:** решения снимают существенные неопределенности.
2. **Принятие дизайна циклов:** оператор принимает предложение с точным хешем.
3. **Включение конфигурации:** активным становится конкретное
   скомпилированное предложение.

Если объединить эти рубежи, гипотеза, генератор или компилятор сможет
авторизовать собственный результат.

## Точная версия результата и данные проверки

Проверяемая версия — точный предмет конкретного запуска. В JSON она называется
`candidate`. Встроенный адаптер репозитория описывает её каноническим
манифестом: перечисляет пути, содержимое, режимы файлов, ссылки, коммиты
подмодулей, ревизию и полный состав. Другой адаптер должен столь же однозначно
определить предмет проверки.

Отчёт проверки называет проверяемую версию, политику, фактическую попытку,
автора, результат, хеш полезной нагрузки, происхождение данных и выполненные
проверки. Совпадение идентификатора не позволяет подменить байты или предмет
проверки.

## Конфигурация и каталог

Действующая конфигурация перечисляет циклы и полномочия. В JSON этот артефакт
называется `binding`. Он содержит точные хеши принятого намерения, журнала
решений, дизайна циклов, реестра и политики. Запуск фиксирует хеш конфигурации,
а не полагается на слово «текущая».

Каталог дописывается только в конец. Включение следующей версии сохраняет
прежние конфигурации, поэтому старые запуски не теряют смысл.

## Собственная конфигурация Concord Loom

Для изменений в своём репозитории Concord Loom использует принятую оператором
конфигурацию:

```text
Observe → Negotiate → Bind → Execute → Verify → Publish → Evolve
```

- **Observe** отделяет факты от предполагаемого намерения.
- **Negotiate** фиксирует решения оператора.
- **Bind** компилирует и отдельно активирует точные циклы, политику и область.
- **Execute** создаёт ограниченный результат и записывает факты исполнения.
- **Verify** независимо проверяет зафиксированную версию результата.
- **Publish** выполняет только явно разрешенный внешний эффект либо фиксирует
  его отсутствие.
- **Evolve** сводит привязанные сигналы в предложение преемника.

Это принятая конфигурация самого Concord Loom, а не обязательная топология для
других проектов.

## Эволюция не авторизует себя

Запуски порождают ограниченные сигналы о трении, сбоях, расхождениях и ритме.
Сигналы можно свести в предложение с предусловиями и риском. Предложение не
может изменить активный каталог или выдать себе право на активацию.

Кто вправе принять следующую версию, определяет действующая конфигурация.
Следующая конфигурация появляется только после отдельного решения
уполномоченного оператора и активации.
